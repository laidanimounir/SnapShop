## فحص الانحراف (drift) — ناجح

قبل أي تعديل، قارنت دالة `place_guest_order` الحية في القاعدة مع الأساس الذي كُتبت منه الهجرة (0012):

- md5 للدالة الحية = `353a0ba490ff5ee3590dcf91edc3308b` وطولها 8897 بايت.
- md5 لنص 0012 في المستودع = **نفس القيمة بالضبط** (وأيضًا بعد مقارنة مُطبَّعة: بدون فراغات/تعليقات).
- النتيجة: **لا يوجد أي انحراف** — الدالة الحية سليمة 100% كما هي في المستودع.

## لماذا توقفنا عند 0017 — بالتفصيل

1. ملف 0017 يضيف معاملًا جديدًا `p_offer_id` إلى `place_guest_order`.
2. في PostgreSQL، جملة `CREATE OR REPLACE FUNCTION` **لا تستطيع تغيير قائمة المعاملات** — بل تُنشئ **دالة ثانية (overload)** بنفس الاسم!
3. النتيجة: صار في القاعدة دالتان: القديمة (10 معاملات) والجديدة (11 معاملة).
4. عند اختبار الاتصال الحقيقي (نفس بيانات الموقع الحالي): 

```
HTTP 300 — PGRST203: Could not choose the best candidate function between:
  place_guest_order(…10 params…), place_guest_order(…10 params…, p_offer_id => uuid)
```

أي: **إرسال الطلبات كان معطلًا في الموقع المباشر** (كل نداء بدون `p_offer_id` يرتد بهذا الخطأ).
5. كل الهجرات السابقة للمستودع (0004 و0007 و0012) تحذف الدالة القديمة **أولًا** بـ `drop function if exists ...` — وتعليق 0012 يقول حرفيًا: *"The 9-arg overload is dropped first so PostgREST never has two candidates for the same call"* — لكن **ملف 0017 لا يحتوي على أي `drop function`**.
6. توقفت فورًا حسب التعليمات، وسُأل المالك، فأمر بتنفيذ فورًا للتراجع — نُفِّذ وتم التحقق:

```
POST /rest/v1/rpc/place_guest_order  →  HTTP 400
{"code":"P0001","message":"Guest name is required"}
```

هذه رسالة من داخل الدالة نفسها = الدالة تُحلَّ وت تعمل مجددًا. (استُخدم حقل فارغ متعمَّد يفشل في التحقق **قبل** أي إدراج — لم يُنشأ أي طلب تجريبي.)

## ترتيب التطبيق المُقرَّر (يكتمل عند إعادة المحاولة)

الترتيب الصحيح: **0015 ← 0016 ← 0017 (بعد إصلاحها) ← 0019 ← 0018 (أخيرًا)**

السبب: ملف 0018 يحتوي على نسخة **أوسع** من دالة 0017 (يضيف جلب `label` + كتابة لقطة العرض في `order_items`). لو طُبِّق 0017 **بعد** 0018 لحُذفت كتابة اللقطة بصمت. لذا 0018 يجب أن يكون دائمًا الأخير. (الترتيب المتوقع في المهمة كان 0017 آخرًا، لكن الملفات تقول العكس — وهذا موثّق هنا).

## تحذيرات الأمان الجديدة (قارن مع خط الأساس)

- **جديد (من 0016) تحذير واحد فقط:** `function_search_path_mutable` على الدالة `enforce_max_quantity_offers` — السبب: الملف لا يضبط لها `set search_path`. الدالة آمنة عمليًا لأنها تستخدم أسماء `public.` مؤهلة، والإصلاح (اختياري) لاحقًا:

## ⚠️ خطوات إلزامية قبل إعادة تطبيق 0017

2. **امحُ سجل الهجرة القديم** من سجل القاعدة (لأن التطبيق نجح ثم تراجعنا — بدون هذا السطر قد يتخطّاه `supabase db push` مستقبلًا):
```sql
delete from supabase_migrations.schema_migrations
where name = '0017_place_guest_order_offer_param.sql';
```
3. **ملف 0019 ينقصه صلاحية للزائر:** سياسة `public read tracking pixel` صحيحة (لا تكشف سوى `key = 'tracking_pixel'`) لكن الجدول **لا يمنح صلاحية SELECT لـ anon أصلًا**، فالزائر لن يقرأ شيئًا حتى بعد تطبيق 0019. أضف هذا الاستعلام ضمن نفس ملف 0019 (أو شغّله بعد التطبيق):
```sql
grant select on public.store_settings to anon;
```
(السياسة تكفي لتبقى باقي الإعدادات مخفية: RLS مفعّل والسياسة تبيح صف `tracking_pixel` فقط.)
4. ثم أعد التفويض: تطبيق **0017 المُصلَّح ← 0019 ← 0018 (آخرًا)**.

## ما يجب فحصه يدويًا (بعد إعادة المحاولة)

1. اطلب منتجًا حقيقيًا من الموقع وأنجح — ثم تأكد من ظهور الطلب في لوحة التحكم.
2. في الأدمن: افتح تعديل منتج — يجب أن يظهر الحقل الجديد "السعر قبل التخفيض" (`compare_at_price`) ولا يقبل قيمة أقل من السعر الحقيقي.

5. جرّب أيضًا الطلب من الهاتف (390px) للتأكد من نموذج الطلب الجديد.
